# Public dataset audit — 2026-09-27

## Decision

**Use Utah FORGE for the next *data-qualification pilot*, not yet for model training or a predictive-accuracy claim.** It is the best directly accessible public combination found of multiple named wells, time-indexed drilling measurements and contemporaneous drilling reports. It is geothermal drilling in Utah, so even a successful within-FORGE result would not establish transfer to Oil India Limited's petroleum wells. The loss-onset labels, complete negative coverage, compatible pre-event features and number of independent positive wells remain unverified.

**Keep Equinor Volve as the petroleum-domain follow-up.** It offers a much broader field release but current access is through Databricks Marketplace and the specific telemetry-to-DDR/label join has not been qualified. Do not substitute a production anomaly or simulated kick dataset for the mud-loss target.

## Direct file inspection: 16A and 56-32

The observations below are **schema/source inspection**, not a measurement-quality audit or label qualification. Only small byte ranges and a public operations summary were inspected; the full telemetry files were not imported or committed.

- [16A 10-second CSV](https://gdr.openei.org/files/1283/16A%2878%29-32_time_data_10s_intervals.csv): the sampled header includes `Time`, `Weight on Bit`, `ROP Depth/Hour`, `Top Drive RPM`, `Top Drive Torque (ft-lbs)`, `Flow In`, `Pit G/L Active`, `Return Flow`, `Total Depth`, and `RigMode`. It does **not** include mud density. The first rows include blanks and `-999.25` sentinels. The time text in those rows is minute-resolution despite the 10-second record interval, so ordering, timezone and report alignment need explicit checks. The server reported 118,580,131 bytes on inspection.
- [16A final mud-log LAS](https://gdr.openei.org/files/1283/16A%2878%29-32%20Final%20mud%20log.las): header states a 130–10,987 ft depth log with 1 ft steps and curves for ROP, WOB, flow in/out, gain/loss, RPM, torque and pit volume. This is a **depth-indexed final log**, not automatically pre-event telemetry. Gain/loss at an anchor must not become a leaked predictor if it was measured after onset. Mud density is not a listed curve.
- [16A summary of daily operations](https://gdr.openei.org/files/1283/Composite-C%20%281%29.pdf): contains a narrative of 9 bbl seepage loss over six hours during drilling from 4,460 to 4,552 ft, and a separate stuck-assembly narrative while drilling from 6,360 to 6,507 ft. These are candidate review passages, **not exact loss-onset timestamps or depths**. A reviewer must establish whether seepage counts as the task's mud-loss event and adjudicate its interval, onset and severity. No label was generated from this text.
- [56-32 10-second CSV](https://gdr.openei.org/files/1295/56-32%2010sec%20data%2027029986.csv): the sampled header has separate date/time, hole and bit depth, WOB, rotary RPM, torque, flow and ROP, but no mud density or explicit loss label. Feature names and measurement definitions differ from 16A, so a shared adapter must document units and missingness. The [catalog](https://catalog.data.gov/dataset/utah-forge-well-56-32-drilling-data-and-logs) also lists DDRs and mud logs.

The current `mud-loss-features-v1` contract requires mud density along with five other features. The inspected public CSV headers do not satisfy it as-is. **Do not silently impute density** or drop it without a versioned feature-contract change and re-reviewed evaluation plan. DDR mud-weight entries might help only if their recorded availability precedes each anchor and their units/datum are verified.

## Qualification sequence and stop rules

1. Record each selected source URL, license, exact bytes/checksum and well identity in the data register. Keep raw files outside Git. Establish whether 16A, 16B, 56-32 and 78B are independent physical wells; do not count sidetracks or duplicate telemetry exports as separate groups.
2. On at least two wells first, audit telemetry timestamp order, timezone, depth reference, units, drilling-state coverage, missing/sentinel values and the exact time a feature becomes available. Join daily reports to telemetry only by reviewed evidence. Exclude operational periods after an event from pre-onset features.
3. Blindly review candidate mud-loss passages and hard negatives. Record onset **ranges** when an exact depth/time is unavailable. A window can be labeled positive/negative only when its full 100 m outcome horizon is observed and the onset definition is resolved. Ambiguous intervals are censored, not forced to a class.
4. Count independent physical wells and positive-event wells before constructing train/validation/test groups. If any split lacks real positive and negative coverage, stop: report a source-qualification result, not model metrics. Do not tune rules or labels on the held-out wells.
5. If this gate passes, implement a FORGE-specific adapter with explicit mappings and `mud-loss-features-v2` only if a documented feature change is necessary. Then run the existing [window validator](README.md), leakage tests, baseline and grouped evaluation. Treat within-FORGE metrics as an exploratory geothermal benchmark; OIL field validation remains separate.

## What the next data request should ask OIL

Request **permitted de-identified data from multiple physical wells**, retaining stable parent/sidetrack IDs, pre-event eRTMAC-compatible telemetry, DDR/WCR source references, mud-loss onset/extent adjudication, formation and MD/TVD/datum records, and explicit reviewed no-event drilling coverage. Ask for data-handling and model-use permissions. A small sample may qualify the adapter but is not automatically enough to train or validate a predictor.
